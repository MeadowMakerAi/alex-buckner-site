FM Command

I built the operating software I use to run my businesses. It started as a tracker for a building renovation. I kept extending it so I could see what had changed, where the information came from and which decisions needed me.

How I built it

I designed the system, wrote the specifications and directed AI coding agents to implement them. Before I ask for a screen, I define the underlying record, what it connects to and who can change it.

FM Command keeps projects, people, equipment and source documents in Postgres. I give each build a written test. The coding agent runs the tests and checks the feature in a signed-in browser. A second AI system reviews the work before it merges.

Trace a delivery change

An email can update what I expect to happen. It takes separate evidence to say that a delivery arrived.

Illustrative demo with fictional messages and dates.

Read the source messages

The contractor’s first email says, “The filler is booked for Thursday.” A follow-up says, “The carrier moved the filler delivery to Friday.” Both messages refer to the same machine.

Inspect the proposed change

The agent proposes changing the filler’s expected delivery from Thursday to Friday. The follow-up email supports that change. Neither message gives an arrival time or confirms receipt.

Check the approved record

Changes learned from email wait for my approval. In this example I accept the new date. The expected delivery now reads Friday and points back to the follow-up email. Receipt remains unconfirmed.

What daily use changed

At first I had to approve each change individually. I couldn’t keep up. I now set permissions according to how easily a change can be undone. An agent can make a reversible update within its remit. A consequential action needs my approval.

I use FM Command daily. Keeping the record current after a text or an in-person conversation is still the hard part.
